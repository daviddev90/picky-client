## Step 1 — 권위 표준에서 추출한 "잘 쓴 지침의 원칙"

읽은 표준: `superpowers:writing-skills`, `skill-creator`, `plugin-dev:skill-development`, `plugin-dev:skill-reviewer`.

- **P1 — 실패-차단(Iron Law):** 지침의 타당성은 *따랐을 때 옳은 산출물이 나오는가*로 검증. (writing-skills)
- **P2 — 결함의 형태에 처방을 맞춰라(Match the Form to the Failure):** (writing-skills)
  - 규칙을 압박 속에 어김 → 금지문 + 합리화표.
  - **따랐는데 산출물 형태가 틀림 → "산출물이 무엇인지" 규정하는 양성 레시피/계약.**
  - **필수 요소 누락 → 템플릿의 필수 슬롯(구조 강제).**
  - **조건부 행동 → 관찰 가능한 술어로 keyed된 조건문.**
  - *금지문은 형태-결함에 역효과*라고 명시.
- **P3 — 규율형 지침은 프로세스를 강제**하고 압박 하에 테스트. 서술만으론 부족. (writing-skills)
- **P4 — "왜"를 설명하라.** 대문자 MUST 남발은 yellow flag. 이유를 알면 새 상황에 *일반화*한다. (skill-creator)
- **P5 — 반복 작업은 공유 자산으로 고정.** (skill-creator)
- **P6 — 지침은 *다른 Claude가 쓰라고* 만든다 → 비자명한 정보(실제 플로우·렌더 사실)를 담아라.** (skill-development)
- **P7 — 리뷰 축:** 구조 / 트리거 / 내용 / 점진적 공개 / 심각도(critical·major·minor). (skill-reviewer)

**핵심:** 이번 실패는 "규칙 위반"이 아니라 — 에이전트가 지침을 **따랐는데** 산출물에 미렌더 요소가 섞인 것 +
생성 전 사고 누락. P2에 따르면 올바른 처방은 **금지문이 아니라** ① 양성 레시피, ② 필수 슬롯, ③ 조건부 게이트.

## Step 2 — 합의된 루브릭 (잣대)

**적용 렌즈(모든 항목 공통):**
- **M0 실패-차단 테스트:** 곧이곧대로 따르는 유능한 에이전트가 이 지침만 보고 관찰된 실패를 낼 수 있으면 결함.
- **M-form 형태 적합성:** 처방이 P2가 요구하는 형태(양성 레시피 / 필수 슬롯 / 조건부 게이트)를 취하는가.

각 항목 = "시안 생성(fan-out) **전에** 강제되는가?"
- **C1** 이번 라운드가 무엇을 결정하는가 명시.
- **C2** 사용자가 실제 어느 화면에서 무엇을 보는가 / 무엇이 렌더되는가(실제 플로우 파일 읽기) 확정.
- **C3** 무엇을 변주·고정하는가(변주 축·고정 목록) 명시.
- **C4** 현재 트렌드 리서치 + 그 반영을 산출물에서 검증.
- **C5** 렌더/가시성 일관성 게이트 — 시안의 모든 요소가 대상 플로우에서 실제 렌더되는가? 미렌더(죽은) 요소 차단.
- **C6** C1~C5가 스킵 불가 게이트로 강제되는가(서술만 X). 스펙 없는 fan-out을 막는가.
- **C7** 각 게이트에 "왜"가 붙어 에이전트가 새 라운드에도 일반화하는가.

## Step 4 — 지침 개선안 (형태 정합·조건부로 정제)

**① [핵심] 후보 저작 계약을 "대상 표면(target-surface) 양성 계약"으로 강화** — `harness.md` candidate authoring
contract + `SKILL.md` 코어루프.
> 후보는 **하나의 명명된 실제 표면**을 충실히 렌더한 것이다. *어느 라우트/화면*을 그리는지, 그 화면에서 *실제로
> 발생할 수 있는 상태만* 명시하고 그것만 그린다.

금지문("페이저 넣지 마")이 아니라 **"산출물이 무엇인지"를 규정하는 양성 레시피**(writing-skills row2). 기존
"representative screen" 계약(harness.md:409)의 씨앗을 강화하는 형태.

**② [핵심] 관찰 술어로 keyed된 좁은 조건부 — 메타/공유-크롬 케이스 한정** — `rounds.md`에 짧은 절 신설.
> 설계 대상이 **형제 화면과 크롬/상태를 공유**할 때(예: 하네스 자신의 리뷰 페이지 재설계, 위저드 한 단계, 공유
> 내비 하위 탭) — 페이저·"현재 보는 중"·진행바 같은 일부 상태는 **형제 표면에 사는 것**이다. 생성 전 실제 플로우
> 파일을 읽어 "이 표면 렌더 vs 형제 표면 렌더"를 갈라라. 형제 표면에서만 발생하는 컨트롤/상태는 이 후보에
> 그리지 않는다(사용자가 그 화면에서 볼 일 없으니 판단 대상이 못 됨). **왜:** [근거 부착].

"공유 크롬/상태" 술어에 keyed되어 **정상 라운드는 자동 스킵** → overfit·관료화 회피(반론 holdsUp 반영).

**③ 메타/재귀 케이스를 스킬이 명시적으로 상정** — "picky-client로 하네스 자신을 설계할 때"를 동기 예시로.
(실패의 결정적 촉발자였고 스킬이 한 번도 안 다룸.)

**④ C3 캐리오버 단서(경량)** — `rounds.md`: "우승작 unchanged 계승은 *결정*을 잇는 것이지 *실수*를 잇는 게
아니다. 대상 표면에서 렌더 안 되는 요소는 캐리오버에서 고친다 — 죽은 컴포넌트를 고정 베이스로 세탁하지 마라."

**⑤ C4 경량화(검증 게이트 금지)** — `rounds.md`: 각 후보 `meta.rationale`에 참고한 트렌드/레퍼런스를 한 줄로
남겨 리서치를 **가시화**. *통과 체크박스로 만들지 않는다*(주관 품질에 인용극장 유발 — 반론 holdsUp). 후속
라운드도 quick refresh.

*(C1·C7은 손대지 않음 — 이미 충족. C7의 "왜 설명" 문화는 유지하며 위 게이트들에도 "왜"를 붙인다.)*
